# Supabase Storage

Three buckets exist in the live project (read from `storage.buckets` on
5 October 2026). All three are **private**: nothing is served by public URL, the
application hands out short-lived signed URLs or streams the bytes itself.

| Bucket | Created | Size limit | MIME restriction | Policies on `storage.objects` |
|---|---|---|---|---|
| `documents` | 10 Feb 2026, by hand in the dashboard (not in any migration) | none | none | any `authenticated` user may SELECT / INSERT / UPDATE / DELETE any object in the bucket |
| `commission-reports` | 7 May 2026, `database-migrations/supabase-phase19e-commission-reports.sql` | 5 MB | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `application/octet-stream` | admin only (`profiles.role = 'admin'`) for all four commands |
| `pack-templates` | 9 Jun 2026, `database-migrations/supabase-phase26-pack-templates-bucket.sql` | none | none | **none**: only the service role can touch it |

## `documents`: the one bucket that holds almost everything

Despite its name, the `documents` bucket is used for four different kinds of
file. The path prefix tells them apart.

| Content | Path pattern | Written by | Read by |
|---|---|---|---|
| Order / quote PDFs | `<userId>/<sanitised client path>.pdf` | `POST /api/documents/upload` with the **user's own session** (RLS applies, hence the permissive bucket policy) | `GET /api/documents/preview` (5-minute signed URL, service role), `POST /api/documents/send-email` (downloads bytes to attach), `GET /api/backup` |
| Agent folder files | `agent-files/<agentId>/<folderId>/<timestamp>-<sanitised name>` (`app/api/agent-folder-files/route.js`) | service role, ≤ 25 MB, PDF / image / Office / txt / csv | `GET /api/agent-folder-files/[id]` (1-hour signed URL) |
| Agent contract PDFs | path stored in `profiles.agent_contract_url` | `POST /api/agents/[id]/contract`, service role, ≤ 10 MB | `GET /api/agents/[id]/contract` (1-hour signed URL), `GET …/contract-text` (text extraction) |
| Organization folder markers | `organizations/<orgId>-<slug>/…/.keep` | `lib/organizations/provisioning.js` (see note below) | nothing; they only make "folders" visible in the dashboard |

The database row for a PDF lives in `public.documents.file_path`. Soft delete
(`deleted_at`) leaves the file in place; `DELETE /api/documents/[id]/purge`
removes both the row and the object. `PUT /api/documents/[id]` replaces the
file and removes the previous object.

**Note on the organization markers.** `lib/organizations/provisioning.js`
writes to the bucket named by `AGENT_DOCUMENTS_BUCKET`, defaulting to
`agent-documents`. That bucket **does not exist** in the live project, so those
writes fail unless the variable points at `documents`. `ensureOrganizationFolders` throws on
the failure, but every caller (`POST /api/organizations`, auto-ensure, member
provisioning) catches it and logs "Folder provisioning error (non-blocking)",
so the organization and its `agent_folders` rows are still created. Check the
server's `.env` for `AGENT_DOCUMENTS_BUCKET=documents` before assuming the
markers exist.

## `commission-reports`

One `.xlsx` per generated report, path stored in
`commission_reports.storage_path`. Written by `lib/commissionReportService.js`
with the service role; downloaded through
`GET /api/commission-reports/[id]/download`, which streams the bytes after
checking the caller is an admin or the report's agent. Deleting the report row
(`DELETE /api/commission-reports/[id]`) also removes the object; the Google
Drive copy is left alone.

## `pack-templates`

One `.xlsx` order form per pack, named `<packId>.xlsx`, generated by
`lib/packTemplates.js` + `lib/packExcel.js` when a pack is created or updated.
Streamed to admins by `GET /api/pack-templates/[id]/download` (regenerated on
the fly if the object is missing). Attached to client emails by
`POST /api/resources/send-email`. There are deliberately no RLS policies: the
anon key cannot list or read these even with a valid session.

## Signed URLs

| Route | Validity |
|---|---|
| `GET /api/documents/preview` | 300 s |
| `GET /api/agent-folder-files/[id]` | 3600 s |
| `GET /api/agents/[id]/contract` | 3600 s |

Signed URLs are generated with the service role, so they work regardless of the
bucket policies. Treat them as bearer tokens: anyone holding the URL can read
the file until it expires.

## Backups

`GET /api/backup` (cron-secret protected, **not currently scheduled**) copies the
listed storage prefixes and about 30 tables as JSON into a dated Google Drive
folder. See [../07-background-jobs.md](../07-background-jobs.md).
